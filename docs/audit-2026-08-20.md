### C1. `domain/knowledge/models.py` imports from `pydantic` — violates layering intent partially

**File:** [`domain/knowledge/models.py`](file:///home/bittusah/Projects/Personal/Intern/atlas/packages/atlas/src/atlas/domain/knowledge/models.py#L16)
**Also:** Every other domain model file.

The layering boundary test (`test_layering_boundaries.py`) checks for I/O libraries (`sqlalchemy`, `httpx`, `asyncpg`, etc.) but does **not** check for `pydantic`. CLAUDE.md says:

> `domain/` imports nothing from Atlas outside itself and nothing from any **I/O library**.

Pydantic is a data validation library, not an I/O library, so this is **technically compliant** with the stated rule. However, ARCHITECTURE.md says:

> `domain/` — may import: **nothing from Atlas, no I/O library** — Contains: Entities, value objects, invariants, **pure computation**

The domain layer is tightly coupled to Pydantic's `BaseModel`, `Field`, and `ConfigDict`. If Pydantic is ever replaced or has a major breaking change, every domain model changes. This is a **design decision to document**, not necessarily a bug — but it should be recorded in an ADR or DECISIONS.md since the spec's wording is ambiguous.

**Risk:** Low immediate, medium long-term.
**Action:** Document the decision that Pydantic is an accepted domain-layer dependency (it is a validation/serialization library, not I/O). Add `pydantic` to the layering test's explicit allowlist with a comment explaining why.

### C3. `LocalStorage` performs synchronous blocking I/O inside `async` methods

**File:** [`adapters/storage/local.py`](file:///home/bittusah/Projects/Personal/Intern/atlas/packages/atlas/src/atlas/adapters/storage/local.py)

All three methods (`put`, `get`, `exists`) are declared `async` but call synchronous filesystem operations:
- `target_file.write_bytes(content)` (line 30)
- `target_file.read_bytes()` (line 39)
- `target_file.exists()` (lines 29, 37, 43)
- `target_dir.mkdir(...)` (line 26)

These will **block the asyncio event loop** when handling large files (source snapshots, rendered videos at ~200MB+). Under concurrent pipeline steps, this will stall the entire worker.

**Risk:** High under real load. A 200MB video snapshot write blocks the event loop for seconds.
**Action:** Use `asyncio.to_thread()` or `aiofiles` to wrap all filesystem I/O. The `Storage` protocol's `async` signatures are correct — the implementation must actually be async.

### C4. GPU resource lock has no row-level locking — TOCTOU race condition

**File:** [`execution_repository.py` lines 244–280](file:///home/bittusah/Projects/Personal/Intern/atlas/packages/atlas/src/atlas/adapters/persistence/repositories/execution_repository.py#L244-L280)

The `acquire_lock` method does:
1. `session.get(ResourceLockTable, resource_name)` — reads current lock
2. Checks if expired or same holder
3. Updates or inserts

Between step 1 and step 3, another concurrent worker could also read the same row, see it as expired, and both workers would "acquire" the lock. This is a classic **Time-of-Check-to-Time-of-Use (TOCTOU)** race.

**Risk:** Critical under concurrent workers. Two GPU-using steps could run simultaneously, causing CUDA OOM crashes.
**Action:** Use `SELECT ... FOR UPDATE` (PostgreSQL row-level exclusive lock) or `INSERT ... ON CONFLICT` with an atomic CAS (compare-and-swap) pattern. Example:
```python
stmt = select(ResourceLockTable).where(
    ResourceLockTable.resource_name == resource_name
).with_for_update()
```

### C5. `conftest.py` uses `drop_all` / `create_all` — bypasses Alembic migration testing

**File:** [`tests/conftest.py`](file:///home/bittusah/Projects/Personal/Intern/atlas/tests/conftest.py)

The test fixture creates tables via `Base.metadata.create_all()` instead of running Alembic migrations. This means:
- Integration tests validate the **ORM model definitions** (`tables.py`), not the **actual migration file** (`0001_initial_schema.py`).
- If `tables.py` and the migration diverge (e.g., a column added to the ORM but not to the migration, or vice versa), tests pass but production breaks.
- Seeded data from `_seed_initial_data()` is not present in integration tests.

The `test_alembic_migrations.py` only checks that migrations run without errors — it doesn't verify schema correctness.

**Risk:** High. Schema drift between ORM and migrations is one of the most common production failures in SQLAlchemy projects.
**Action:** Add a test that compares `Base.metadata` against the actual Alembic `head` revision using `alembic --autogenerate` and asserts zero detected changes. Or switch integration tests to run migrations instead of `create_all`.

### S1. `Topics` table has no FK to `domains` — referential integrity gap

**File:** [`tables.py` TopicTable](file:///home/bittusah/Projects/Personal/Intern/atlas/packages/atlas/src/atlas/adapters/persistence/tables.py#L49-L55) and [`0001_initial_schema.py` line 84](file:///home/bittusah/Projects/Personal/Intern/atlas/packages/atlas/src/atlas/adapters/persistence/alembic/versions/0001_initial_schema.py#L84)

### S3. `BlackoutRule` semantics are inverted from SPEC

**File:** [`domain/publishing/models.py` BlackoutRule](file:///home/bittusah/Projects/Personal/Intern/atlas/packages/atlas/src/atlas/domain/publishing/models.py#L57-L62)

The model has:
```python
local_start_time: time = Field(default=time(6, 0), description="Earliest allowable publish time (06:00)")
local_end_time: time = Field(default=time(22, 0), description="Latest allowable publish time (22:00)")
```

This defines an **allowed window** (06:00–22:00), but the class is named `BlackoutRule` and the spec says:

> **Blackout:** no slot before 06:00 or after 22:00 audience-local.

The naming and semantics conflict. Is `local_start_time` the start of the blackout or the start of the allowed window? The description says "earliest allowable" which means it's an allowed-window, but the class name says "blackout." This **will** cause confusion when writing the scheduling logic in Phase 8.

**Risk:** Semantic confusion leading to inverted logic bugs in Phase 8 scheduling.
**Action:** Rename fields to `earliest_allowed_time` / `latest_allowed_time`, or rename the class to `PublishingConstraint`, or add a prominent docstring clarifying the semantics.

### S4. ID truncation to 16 hex chars reduces UUID collision resistance

**File:** [`platform/ids.py` line 10](file:///home/bittusah/Projects/Personal/Intern/atlas/packages/atlas/src/atlas/platform/ids.py#L10)

```python
clean_hex = uuid.uuid4().hex[:16]
```

UUID4 has 122 bits of randomness (32 hex chars). Truncating to 16 hex chars leaves 64 bits. By the birthday paradox, there's a ~50% collision probability at ~2^32 (~4 billion) IDs. That's safe for this scale, but:

- `generate_trace_id()` uses the **full** 32 hex chars, creating inconsistency.
- At 3 videos/day with ~50 entities per run, that's ~150 IDs/day or ~55,000/year. Collision probability is negligible at this scale but the choice should be documented.

**Risk:** Low for current scale.
**Action:** Document the ID length decision. Consider using the full UUID hex for all IDs for consistency with `trace_id`.

### S7. `database.py` instantiates `Settings()` at module import time

**File:** [`database.py`](file:///home/bittusah/Projects/Personal/Intern/atlas/packages/atlas/src/atlas/adapters/persistence/database.py) via [`config.py` line 35](file:///home/bittusah/Projects/Personal/Intern/atlas/packages/atlas/src/atlas/platform/config.py#L35)

`config.py` has `settings = Settings()` at module level. This means:
- Importing `database.py` → imports `config.py` → instantiates `Settings()` → reads `.env` and environment variables.
- During testing, `conftest.py` hardcodes `TEST_DATABASE_URL` directly, bypassing `settings`. This works but means there's no way to configure the test database via environment variables.

**Risk:** Medium. Import-time side effects break test isolation and make CI configuration fragile.
**Action:** Use a lazy singleton pattern or `@lru_cache` function instead of module-level instantiation.

## 🔵 OBSERVATIONS (Not Defects)

### O1. Dual ORM-Migration maintenance burden
Both `tables.py` (ORM models) and `0001_initial_schema.py` (Alembic migration) define the same schema independently. Changes must be made in both places. This is standard SQLAlchemy practice but is the most common source of production schema drift. See C5 for the testing gap.

### O2. No `packages/fakes/` directory yet
ARCHITECTURE.md §9 specifies a `packages/fakes/` package for deterministic provider doubles. Not needed for Phase 2 but required before Phase 3's "Run traverses every stage with fake providers" acceptance criterion.

### O3. No `apps/` directory yet
The folder layout in ARCHITECTURE.md shows `apps/api/`, `apps/worker/`, `apps/cli/`. Phase 3 will need these entrypoints.

### O4. `domain/publishing/models.py` defines `PublishSlot` which has no table
`PublishSlot` is a domain model with no corresponding table, repository, or test. It exists as a forward-looking type for Phase 8. This is fine as a seam but should be noted.

### O5. `ResourceLockTable` uses single-row primary key — no queueing
The current design supports exactly one lock per resource name. If multiple workers want to queue for the GPU (rather than fail immediately), a queue mechanism would need additional rows.

### O6. Alembic migration uses hardcoded datetime for seeds
```python
now = datetime(2026, 7, 30, 0, 0, 0, tzinfo=UTC)
```
This is fine for a seed (deterministic and reproducible) but worth noting that it's intentionally static rather than using `sa.func.now()`.

### O7. The `platform/` layer imports `pydantic_settings` — correctly outside `domain/`
This is noted as correct behavior per the layering rules. `platform/config.py` uses `pydantic-settings` which is listed in the forbidden imports for `domain/` but allowed in `platform/`.

### 3. Debugging Retrospective: The Alembic Configuration Bug
During remediation, `pytest` failed with `UndefinedTableError: relation "channels" does not exist`. 
- **Root Cause:** In `alembic/env.py`, `config.get_main_option("sqlalchemy.url")` was taking precedence over environment variables / test config objects. Alembic was running migrations against the main `atlas` database instead of `atlas_test` during test execution! Furthermore, because `Base.metadata.drop_all` was previously called in teardown, `alembic_version` remained in `atlas_test`, causing Alembic to think migrations were already applied when they were not.
- **Solution:** 
  1. Updated `alembic/env.py` to prioritize test-injected settings.
  2. Updated `conftest.py` teardown to use `command.downgrade(alembic_cfg, "base")` to clean up `alembic_version`.
